# Core PMS (milestone 2) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans. Steps use checkbox syntax. Every task is test-first: write the failing test, watch it fail, write the code, watch it pass.

**Goal:** Staff run a hotel's day in the app: rooms and rates, reservations, check-in and check-out, the folio with payments recorded by hand, housekeeping and maintenance, alerts with one-button fixes, and team notes on bookings.

**Architecture:** New Go packages (`rooms`, `booking`, `folio`, `housekeeping`, `alerts`, `notes`) mounted in `internal/app`, each with its own migration and row-level security by organization. Inventory is guarded twice (spec 03): a `CHECK` per room type and night, and an exclusion constraint per room. Alerts are plain rules run by a sweeper, reusing `notify`. The web app fills in the Calendar, Arrivals, Guests, Payments, Rates, Rooms and Issues screens of the existing shell.

**Tech Stack:** As milestone 1. Adds PostgreSQL `btree_gist` for the exclusion constraint.

**Spec:** `docs/specs/03-data-model.md`, `06-payments.md` (hand-recorded methods only), `09-alerts-and-suggested-actions.md`, `11-team-notes.md`, `01-roles-and-access.md`, and the design doc.

## Global Constraints

- Money is an integer in the currency's smallest unit beside a 3-letter code. Never floats.
- Times in UTC. A "hotel day" is a date in the property's time zone.
- Primary keys are UUID v7 (`ids.New()`). Every table has `organization_id` and row-level security (`enable` and `force`, as in milestone 1, unless a ruling says otherwise).
- Every write route records an audit entry in its own transaction (`audit.Record`).
- Every error shown to a person has copy in `web/messages/en.json`. No literal design values in components (`tokens.test.ts`).
- Strict TDD. Mutation-check the money and inventory rules.

## Scope decisions (rulings, argued from the spec)

- **Card payments and the guest booking page are milestone 3.** Here the folio takes payments recorded by hand: cash, card terminal, bank transfer, other (spec 06, "At the front desk").
- **Checks that need channels** (overbooking risk, channel failing or down, compare difference, unmapped, rate gap pickup checks) wait for milestone 4. Pickup checks also wait (they need 8 weeks of data).
- **Photos on notes, shift handover and note search** wait for milestone 5 (uploads) and milestone 6.
- **Tours and products on the folio** wait for milestone 5. The folio has `extra` lines but no catalog yet.

## Review Focus

1. Two staff book the last room at the same moment: exactly one succeeds, `sold` never exceeds `total`.
2. A checkout and a check-in on the same date in the same room are both accepted; two overlapping stays in one room are refused.
3. Cancelling twice, or checking in twice, changes things once.
4. A housekeeper never receives a guest name, contact detail or price in a note, task or notification.
5. A refund larger than what is left, or above the role's limit without approval, is refused.

### Task 1: Rooms, room types, rate plans, rates

**Files:** Create `api/migrations/0013_rooms.sql`, `api/internal/rooms/{rooms.go,rates.go,handlers.go,rooms_test.go}`. Modify `internal/app/app.go`.

**Interfaces:**
- Produces tables `room_type`, `room`, `rate_plan`, `rate`, `inventory`, `tax_rule` (spec 03). `inventory.total` follows the count of rooms of a type that are not out of order for that night.
- `rooms.Mount` routes: `GET/POST /api/room-types`, `PATCH /api/room-types/{id}`, `GET/POST /api/rooms`, `PATCH /api/rooms/{id}`, `GET/POST /api/rate-plans`, `GET /api/rates?from&to&ratePlanId`, `PUT /api/rates` (a range with price, min nights, closed flags). Permissions: `rates.edit` for rates and plans, `housekeeping.update` is not enough for rooms; room types and rooms need `users.manage`-level manager rights (use `RatesEdit` for rates, `UsersManage` for room types and rooms; ruled).
- `rooms.EnsureInventory(ctx, tx, roomTypeID, from, to)` fills `inventory` rows for a date range. `rooms.Price(ctx, tx, ratePlanID, from, to, adults, children) ([]Night, total int64, error)` applies the extra-guest rule from spec 03.

- [ ] Test: creating a room type then rooms raises `inventory.total` for the next 365 days; a rate range sets one `rate` row per date; `Price` adds extra adult and child prices above `base_guests` and refuses above `max_guests`; rates below half or above 3 times the room type average are saved but flagged (`suspicious`).
- [ ] Test: another organization's rooms and rates are invisible; a front desk user gets 403 on writes.
- [ ] Implement, run, commit.

### Task 2: Guests and reservations with the inventory guards

**Files:** Create `api/migrations/0014_reservations.sql` (enables `btree_gist`), `api/internal/booking/{booking.go,create.go,handlers.go,booking_test.go}`.

**Interfaces:**
- Tables `guest`, `reservation`, `reservation_room`, `reservation_night` (spec 03) with the exclusion constraint on `(room_id, stay)` for active rows.
- `booking.Create(ctx, tx, in CreateInput) (Reservation, error)` where `CreateInput{PropertyID, Guest GuestInput, Rooms []RoomRequest{RoomTypeID, RatePlanID, From, To, Adults, Children}, Source string}`. It locks `inventory` rows in date order, adds to `sold`, writes nights with prices, a unique reservation `code`, and an audit entry. A full night returns `booking.ErrSoldOut`.
- Routes: `POST /api/reservations`, `GET /api/reservations?from&to&status&q`, `GET /api/reservations/{id}`, `POST /api/reservations/{id}/cancel`, `GET /api/availability?from&to`, `GET /api/guests?q`, `GET/PATCH /api/guests/{id}`. Permissions: `reservations.view` and `reservations.edit`; guest contact needs `guests.contact.view`.

- [ ] Test: 20 concurrent bookings for the last room: exactly 1 succeeds, `sold` equals `total`.
- [ ] Test: booking and its inventory change roll back together; cancel lowers `sold` once and a second cancel changes nothing.
- [ ] Test: the same guest email (any case) in one organization is one `guest`; a chain's other property reuses the profile.
- [ ] Test: housekeeping gets 403; front desk reads guest contact, revenue does not.
- [ ] Implement, run, commit.

### Task 3: Room assignment, check-in, check-out, no-show

### Task 4: Folio, tax, payments by hand, refunds

**Files:** Create `api/migrations/0015_folio.sql`, `api/internal/folio/{folio.go,handlers.go,folio_test.go}`.

**Interfaces:**
- Tables `folio`, `folio_line`, `payment`, `refund`, `refund_limit` (per property and role). A folio is created with the reservation and receives `room` lines (one per night) and `tax` lines from `tax_rule`. Total is always the sum of lines (a view, never stored).
- Routes: `GET /api/reservations/{id}/folio`, `POST /api/folios/{id}/lines` (adjustment or extra), `POST /api/folios/{id}/payments {method, amount, note}`, `POST /api/payments/{id}/refunds {amount, reason}`, `POST /api/refunds/{id}/approve`.
- Rules: methods `cash`, `card_terminal`, `bank_transfer`, `other`; a refund above what is left is refused; above the role's limit it waits for approval by a manager or owner; every refund has a reason and an audit entry; balance = lines minus payments plus refunds.

- [ ] Tests: sum of lines equals total; tax inclusive and added on top; payment lowers balance; refund over remaining refused; refund over the limit pending until approved; front desk cannot approve.
- [ ] Implement, run, commit.

### Task 6: Alerts engine and the core checks

**Files:** Create `api/migrations/0017_alerts.sql`, `api/internal/alerts/{alerts.go,checks.go,handlers.go,alerts_test.go}`.

**Interfaces:**
- Tables `alert` (unique on property, check kind and subject while open) and `check_setting`. `alerts.Run(ctx, pool, now)` evaluates every enabled check per property, opens, updates and closes alerts, and sends a notification (`notify.Send`) to the target role with key `alert:{id}`.
- Checks in this milestone: unassigned arrival, room not ready, unpaid arrival, unpaid departure, late checkout, likely no-show, out-of-order clash, repeat issue, returning guest, refund waiting.
- Routes: `GET /api/alerts` (only for the person's role), `POST /api/alerts/{id}/{accept|dismiss|snooze}`, `GET/PUT /api/check-settings`. A suggested action is a structured preview plus an `apply` route that does exactly what the preview said and writes an audit row with the alert id.

- [ ] Tests per spec 09: each check raises one alert when its trigger is met and none otherwise; a trigger that stays true does not make a second alert; the alert closes on its own when fixed; a non-target role cannot read it; turning a check off closes its alerts; a dismissed alert stays away 24 hours; an applied action writes an audit row linked to the alert.
- [ ] Implement, run, commit.
